# Codegen Architecture

## Overview

The code generator replaces the legacy GSL (iMatix Generator Scripting Language) pipeline with a Python-based system. It reads XML source models, builds a typed Intermediate Representation (IR), and emits code for C libraries and 6 wrapper languages.

## Pipeline Stages

### Stage 1: Source Loading (`project_source.py`)

Reads XML files from `codegen/models/project_*/` and produces a `ProjectSource` object — a thin wrapper around the raw XML tree with accessor methods for entities, features, and project metadata.

**Input**: `codegen/models/project_foundation/project_foundation.xml`
**Output**: `ProjectSource` with all entity definitions, dependencies, and wrapper declarations

### Stage 2: IR Construction (`project_ir.py`)

Transforms `ProjectSource` into `IRProject` — a fully typed, normalized representation.

Key IR types:
- `IRProject` — top-level: name, prefix, namespace, framework, all entity lists
- `IRClass` — class with methods, constructors, dependencies, struct fields, constants
- `IRImplementation` — concrete implementation with interface bindings
- `IRInterface` — protocol/interface with method signatures and constants
- `IREnum` — enumeration with named constants
- `IRCMethod` — method with arguments, returns, visibility, code blocks
- `IRCArgument` — argument with full type metadata (class_name, interface_name, enum_name, type_name, access, length_attrs)

The IR resolves:
- Default values for `access`, `is_reference` based on type kind
- Cross-project references via `fallback_projects`
- Output file paths for each entity

### Stage 3: Backend Generation

Each backend consumes `IRProject` and produces a list of `(path, content)` tuples:

```python
generate_{lang}_files(project_ir: IRProject, license_text: str = "", repo_root: str = ".") -> list[tuple[str, str]]
```

**All backends are pure functions** — they read from IR only, never from the filesystem.

### Stage 4: Orchestration (`common_bootstrap.py`)

- Loads the project source model
- Builds the IR
- Dispatches to C, CMake, and wrapper backends based on the `wrappers=` XML attribute
- Writes output files to disk
- Supports `--apply` (write to repo) and `--out` (write to temp directory)

## IR Design Principles

1. **No per-project branching** — the IR normalizes all projects into the same shape
2. **Wrapper-ready metadata** — `length_attrs` for buffer capacity, `access` for ownership semantics
3. **Cross-project resolution** — `fallback_projects` provides type info from dependency projects
4. **Constant expression resolution** — `resolve_constant_value()` evaluates GSL refs and arithmetic

## Method Body Generation Pattern

Each wrapper backend generates method bodies by:

1. **Filtering** methods via `_method_should_wrap()` (scope, declaration, visibility)
2. **Classifying** arguments: data inputs, buffer outputs, error args, interface refs
3. **Building** the C function call from entity name + method name + prefix
4. **Marshalling** each argument from the target language to C
5. **Handling** the return: status check, buffer extraction, type conversion
6. **Resolving** buffer capacity from `length_attrs` (method calls, constants, cross-class refs)

The Go backend (`project_go_backend.py`, 2787 lines) is the reference implementation — it was the first wrapper ported and has the most mature method body generation.

## Entity-to-File Mapping

| Entity         | C                                   | Go                | Swift                          | Python               | Java                | PHP                | WASM  |
| -------------- | ----------------------------------- | ----------------- | ------------------------------ | -------------------- | ------------------- | ------------------ | ----- |
| Enum           | `.h` + `.c`                         | `.go`             | `.swift`                       | `_c_bridge/` + `.py` | `.java`             | `.php`             | `.js` |
| Interface      | `.h` + `.c` + `_api.h/.c`           | `.go` (interface) | `.swift` (protocol)            | abstract `.py`       | `.java` (interface) | `.php` (interface) | `.js` |
| Class          | `.h` + `.c` [+ `_defs.h/.c`]        | `.go` (struct)    | `.swift` (class)               | bridge + `.py`       | `.java` + JNI       | `.php` + C ext     | `.js` |
| Implementation | `.h` + `.c` + `_defs` + `_internal` | `.go` (struct)    | `.swift` (class + conformance) | bridge + `.py`       | `.java` + JNI       | `.php` + C ext     | `.js` |

| File                                                     | Purpose                                  | Generated by     |

| `{prefix}_api.h/.c`                                      | Generic API type (when interfaces exist) | C backend        |
| `{prefix}_impl.h/.c`                                     | Generic impl type                        | C backend        |
| `context.go` / `CContext.swift`                          | Context protocol/interface               | Go/Swift backend |
| `{project}_error.go/.swift/.js/.py`                      | Error handling                           | Each backend     |

| `sources.cmake` / `features.cmake` / `definitions.cmake` | Build system                             | CMake backend    |

## Cross-Project References

Projects reference types from other projects (e.g., ratchet uses foundation's `PrivateKey`).

Resolution chain:
1. Check `arg.project` — if set, it names the defining project
2. Look up in `IRProject.fallback_projects` for prefix/namespace
3. Fall back to `_PROJECT_PREFIX_MAP` (static table)

Each backend handles cross-project refs differently:
- **Go**: `import foundation "virgil/foundation"` + qualified types
- **Swift**: `import VirgilCryptoFoundation` + unqualified types
- **Python**: `from virgil_crypto_lib.foundation._c_bridge import vscf_impl_t`
- **Java**: `import com.virgilsecurity.crypto.foundation.*`
- **WASM**: `modules.FoundationInterface` (runtime dispatch)
- **PHP**: `\Virgil\CryptoWrapper\Foundation\` namespace

## Testing Strategy

Each backend has unit tests that verify:
1. **File counts** — correct number of files generated per project
2. **Structural content** — key patterns present (class names, method signatures)
3. **Parity** — enum files match legacy output (Go, Swift)

Integration tests run the full pipeline: generate → build → run crypto operations.
