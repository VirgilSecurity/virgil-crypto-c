# vscf_key_alg_factory returns NULL for ML-KEM-768 and ML-DSA-65 algorithm IDs

## Problem

When ML-KEM-768 and ML-DSA-65 were added to the foundation library, the `switch` statements in `vscf_key_alg_factory.c` were not extended to cover the new algorithm IDs or implementation tags. Every call path that needed to instantiate a key algorithm object for these algorithms fell through to the `default:` branch and returned `NULL` with `ERROR_UNSUPPORTED_ALGORITHM`, with no compile-time indication that anything was wrong. The ratchet layer (`vscr_ratchet_pb_utils.c`) was already calling the factory with `vscf_alg_id_ML_KEM_768` and receiving `NULL`, which would have caused a NULL-dereference at runtime when importing keys from a serialized session.

## Symptoms

- `vscf_key_alg_factory_create_from_alg_id(vscf_alg_id_ML_KEM_768, NULL, &error_ctx)` returns `NULL`; `error_ctx.status` is `vscf_status_ERROR_UNSUPPORTED_ALGORITHM`
- `vscr_ratchet_pb_utils.c` calls this factory at the ML-KEM public/private key import sites and receives `NULL`, causing a NULL-dereference when calling methods on the returned `vscf_impl_t *`
- `vscf_key_alg_factory_create_from_key()` with any ML-KEM or ML-DSA key also returns `NULL`, breaking higher-level operations (`vscf_key_provider_import_public_key`, `vscf_signer`, `vscf_verifier`, `vscf_recipient_cipher`) that route through the factory by impl tag
- The factory already had correct cases for `vscf_alg_id_FALCON` / `vscf_impl_tag_FALCON` — the new algorithms were simply not placed alongside it
- No compile error, no static analysis warning; the failure is a pure runtime NULL

## What Didn't Work

The presence of Falcon cases inside `#if VSCF_POST_QUANTUM` gave the visual impression that post-quantum support in the factory was complete. The `#if` guard block existed and was correct — the problem was the absence of `case` labels for the two new algorithms inside it. Grepping for `ml_kem` or `ml_dsa` in `vscf_key_alg_factory.c` would have immediately revealed the gap, but this search was not performed as part of the initial algorithm integration. The factory is hand-written C (not generated by codegen), so it was not updated during the codegen-model removal step of the round5 migration. (session history)

## Solution

**File:** `library/foundation/src/vscf_key_alg_factory.c`

**Step 1 — Add includes** in the user-editable section above `@generated`:

```c
#include "vscf_ml_kem.h"
#include "vscf_ml_dsa.h"
```

**Step 2 — Add cases to `create_from_alg_id()`** inside `#if VSCF_POST_QUANTUM`, alongside the existing Falcon case:

```c
#if VSCF_ML_KEM
    case vscf_alg_id_ML_KEM_768: {
        vscf_ml_kem_t *ml_kem = vscf_ml_kem_new();
        if (random) {
            vscf_ml_kem_use_random(ml_kem, (vscf_impl_t *)random);
        }
        return vscf_ml_kem_impl(ml_kem);
    }
#endif // VSCF_ML_KEM

#if VSCF_ML_DSA
    case vscf_alg_id_ML_DSA_65: {
        vscf_ml_dsa_t *ml_dsa = vscf_ml_dsa_new();
        if (random) {
            vscf_ml_dsa_use_random(ml_dsa, (vscf_impl_t *)random);
        }
        return vscf_ml_dsa_impl(ml_dsa);
    }
#endif // VSCF_ML_DSA
```

**Step 3 — Add cases to `create_from_key()`** alongside `vscf_impl_tag_FALCON`:

```c
    case vscf_impl_tag_ML_KEM:
        return vscf_key_alg_factory_create_from_alg_id(vscf_alg_id_ML_KEM_768, random, error);

    case vscf_impl_tag_ML_DSA:
        return vscf_key_alg_factory_create_from_alg_id(vscf_alg_id_ML_DSA_65, random, error);
```

## Why This Works

`vscf_key_alg_factory` is the single dispatch point mapping an algorithm identifier (or a live key object's impl tag) to its corresponding algorithm implementation. Every higher-level operation that imports, exports, or manipulates a key calls through this factory. ML-KEM-768 and ML-DSA-65 had full `vscf_ml_kem_t` and `vscf_ml_dsa_t` implementations — adding the `case` labels makes the factory aware of them so all callers receive a fully-initialized algorithm object instead of `NULL`. The `#if VSCF_ML_KEM` / `#if VSCF_ML_DSA` guards mirror the Falcon pattern, ensuring the cases compile away cleanly when an algorithm is disabled at build time. Both `create_from_alg_id` and `create_from_key` must be updated together: fixing only the impl-tag switch would leave the alg-id path broken for any caller that goes through `create_from_alg_id` directly (as `vscr_ratchet_pb_utils.c` does).

## Prevention

Checklist when adding a new algorithm to the foundation library:

1. Implement `vscf_<alg>.c` / `vscf_<alg>.h` with `_new()`, `_impl()`, `_use_random()`, etc.
2. Add `vscf_alg_id_<ALG>` to `enum_alg_id.xml` and `vscf_impl_tag_<ALG>` to the impl tag enum; regenerate.
3. **Open `library/foundation/src/vscf_key_alg_factory.c` and add both:**
   - A `case vscf_alg_id_<ALG>:` block in `create_from_alg_id()` inside the appropriate `#if` guard
   - A `case vscf_impl_tag_<ALG>:` line in `create_from_key()`
4. Add the corresponding `#include "vscf_<alg>.h"` in the user-editable section of the factory file.
5. Search for the nearest sibling algorithm (e.g., Falcon for a new PQ algorithm) in the factory and confirm the new algorithm is placed alongside it.
6. Write a round-trip test (`generate → factory create → export → import → compare`) that goes through the factory to catch gaps immediately rather than at runtime.
7. Note: `vscf_key_alg_factory.c` is **hand-written**, not generated by codegen. It will not be updated automatically during codegen model changes and must be updated manually at the same time as the codegen models.
