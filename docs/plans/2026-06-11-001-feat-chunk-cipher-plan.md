# feat: Add vscf_chunk_cipher — per-chunk AES-256-GCM streaming cipher

## Overview

Add `vscf_chunk_cipher` — a new standalone class in `library/foundation` that encrypts data in configurable fixed-size chunks using AES-256-GCM. Each encrypted chunk is a self-contained frame carrying its own GCM authentication tag. Per-chunk nonces are derived deterministically from an initial nonce (stored in CMS custom params) and an 8-byte counter, following the TLS 1.3 nonce construction. This enables streaming encryption/decryption with bounded memory, per-chunk integrity verification, and random-access chunk decryption.

The class is a pure streaming primitive — it takes a raw 32-byte AES-256 key and an initial nonce, and performs no key wrapping, recipient management, or metadata embedding in the ciphertext stream. Metadata (`initial_nonce`, `chunk_size`) is stored in `vscf_message_info` custom params by the caller.

## Problem Frame

The existing `vscf_recipient_cipher` is a high-level composition that wraps key management, recipient logic, and symmetric encryption. Applications that need to encrypt large streaming data with bounded memory usage, detect tampering at chunk granularity, or seek within a ciphertext stream have no suitable primitive in `library/foundation`.

The historical `VirgilChunkCipher` (predecessor C++ library) solved this at the application layer. This plan adds an equivalent C-level primitive to the foundation library for use by higher-level compositions and language wrappers.

## Requirements Trace

- R1. Each encrypted chunk frame carries a 16-byte GCM authentication tag; decryption verifies the tag before yielding plaintext
- R2. Chunk size is configurable (default 65536 bytes); `chunk_size` and `initial_nonce` are stored in `vscf_message_info` custom params by the caller — the raw ciphertext stream contains only frames
- R3. Streaming API: `process_encryption`/`process_decryption` accept arbitrary-length input; the class accumulates data internally and flushes complete frames
- R4. Per-chunk nonces are derived deterministically: `nonce_i = initial_nonce XOR (0x00000000 || uint64_be(i))`; the 8-byte counter `i` is stored in each frame and also used as GCM `auth_data` to authenticate chunk ordering
- R5. The class accepts a raw 32-byte AES-256 key and a 12-byte initial nonce; no key wrapping, recipients, or password derivation
- R6. `initial_nonce` is generated by `start_encryption` via the injected `random` dependency and exposed via a `nonce()` accessor for the caller to store in CMS; on decrypt the caller sets it via `set_nonce()` after reading from CMS
- R7. All generated scaffolding (headers, `_internal.c`, `_defs.c`, public header inclusion) is produced by `python3 -m tools.codegen.common_bootstrap --project foundation --apply` from the XML model
- R8. Full C test suite covering round-trip correctness, stream reassembly at varying granularity, tamper detection, and counter-binding validation; includes known-answer test vectors

## Scope Boundaries

- No key wrapping, recipient management, or password derivation (left to `vscf_recipient_cipher` or higher-level composition)
- No integration with `vscf_alg_factory` or `vscf_alg_id` enum (composition class, not a raw algorithm implementor)
- No AES-128-GCM variant (AES-256 only, matching the only GCM cipher available in foundation)
- No embedded metadata in the raw ciphertext stream — frame output is purely `counter[8] | ciphertext | tag[16]`

### Deferred to Separate Tasks

- CMS integration layer: writing/reading `initial_nonce` and `chunk_size` to/from `vscf_message_info` custom params — this is the caller's responsibility; `vscf_chunk_cipher` exposes `nonce()` / `set_nonce()` for that handshake
- Language wrapper bindings (Go, Java, Swift, Python): separate task after the C class is merged and stable
- Pre-built static lib rebuild for Go wrapper: handled by `release.yml` workflow_dispatch at release time; no Go code calls the new symbols so Go CI is unaffected during development

## Key Technical Decisions

- **Standalone `<class>`, not an implementor entry**: `vscf_chunk_cipher` is modeled as a `<class>` (like `vscf_recipient_cipher`) rather than an `<implementation>` under `implementor_mbedtls`. Rationale: it composes `vscf_aes256_gcm` rather than being a raw algorithm; it does not implement `alg`, `cipher`, or `cipher_auth` interfaces.
- **Deterministic per-chunk nonce (TLS 1.3 construction)**: `nonce_i = initial_nonce XOR (0x00000000 || uint64_be(i))`. Rationale: single random call per encryption session (for `initial_nonce`); no per-chunk random overhead; nonces are fully determined by the initial nonce and chunk index, so the decryptor needs no per-frame nonce delivery. Equivalent security to random-per-chunk nonces given a fresh random `initial_nonce` per session.
- **8-byte counter in each frame**: The counter `i` (uint64, little-endian) is written as the first 8 bytes of each frame. Rationale: enables random access without tracking sequential state; the counter is also passed as GCM `auth_data` so the tag authenticates chunk ordering — reordered or spliced frames fail verification. With 2^64 chunks at 64 KB, practical limit is ~1.2 × 10²¹ bytes per encryption, far exceeding any real use case.
- **Counter as GCM `auth_data`**: The 8-byte counter value (same bytes written to the frame) is passed to `vscf_aes256_gcm_set_auth_data` before each `auth_encrypt`/`auth_decrypt`. Rationale: prevents an adversary from reordering frames or swapping chunks between two encryptions of the same key — the tag covers both the ciphertext and the chunk's position. No additional API surface needed.
- **No metadata in the raw ciphertext stream**: The `initial_nonce` (12 bytes) and `chunk_size` are stored in `vscf_message_info` custom params by the caller, not embedded as a stream prefix. Rationale: cleaner separation of concerns — `vscf_chunk_cipher` is a pure streaming primitive; the CMS envelope layer handles all metadata. The cipher exposes `nonce()` and `nonce_len()` accessors so the caller can transfer the generated nonce to CMS after `start_encryption`.
- **Default chunk size 65536 bytes (64 KB)**: Balances streaming granularity against overhead (24-byte overhead per chunk = 0.037% at 64 KB). Configurable via `set_chunk_size`.
- **No `alg_id` registration**: Composition class; `vscf_key_alg_factory` and `vscf_alg_id` are unaffected.

## Open Questions

### Resolved During Planning

- **Does chunk cipher need an `alg_id`?** No — composition class, not a raw algorithm. `vscf_key_alg_factory` and `vscf_alg_id` are unaffected.
- **Is the final partial chunk padded to `chunk_size`?** No — AES-GCM produces ciphertext of the same length as plaintext. The final frame is simply shorter; the decryptor detects it by reaching end-of-stream.
- **How does the decryptor know `chunk_size` for frame boundaries?** From `vscf_message_info` custom params, set via `set_chunk_size()` before `start_decryption`. The caller reads this from CMS after deserializing the message info.
- **Should the counter be big-endian or little-endian in the frame?** Little-endian, consistent with the project's existing conventions (e.g., `chunk_size_le32` used in prior designs). The nonce derivation uses `uint64_be` internally (matching TLS 1.3), but the counter written to the frame is `uint64_le` for storage. The nonce derivation may use either endianness consistently — confirm against `vscf_aes256_gcm` nonce byte order convention during implementation.
- **Is a zero-length plaintext chunk valid as EOF marker?** Not required — end-of-stream is implicit. `finish_encryption` encrypts remaining bytes in pending (which may be a partial chunk); `finish_decryption` verifies the pending buffer is empty.

### Deferred to Implementation

- **Exact CMake dependency expression**: Whether `VSCF_CHUNK_CIPHER` should declare a CMake dependency on `VSCF_CTR_DRBG` in addition to `VSCF_AES256_GCM`. Determine from the `VSCF_RECIPIENT_CIPHER` dependency block in `features.cmake`.
- **Pending buffer implementation**: Whether the pending-data accumulation buffers reuse `vsc_buffer_t` or use fixed-size arrays. Determine from how `vscf_recipient_cipher` handles its internal streaming buffers.
- **Codegen snapshot test count increments**: Exact new values for impl-tag count and class count in `tools/codegen/tests/` — determined after running codegen in Unit 3.
- **Counter endianness in nonce XOR**: Whether to XOR the counter as `uint64_be` (TLS 1.3 style) or `uint64_le` — pick one consistently and document in a comment; either is correct as long as encrypt and decrypt agree.
- **Empty input handling**: Whether `process_encryption` with zero-length input is a no-op or an error — follow the `vscf_recipient_cipher` precedent.

## High-Level Technical Design

> *This illustrates the intended approach and is directional guidance for review, not implementation specification. The implementing agent should treat it as context, not code to reproduce.*

### Stream layout

```
Raw ciphertext stream (no header — metadata lives in CMS custom_params):
  FRAME 0:  counter_le64[8] | ciphertext[chunk_size] | tag[16]
  FRAME 1:  counter_le64[8] | ciphertext[chunk_size] | tag[16]
  ...
  FRAME n:  counter_le64[8] | ciphertext[remaining_bytes] | tag[16]

Frame overhead: 8 (counter) + 16 (tag) = 24 bytes per chunk

CMS custom_params (managed by caller, not by vscf_chunk_cipher):
  "chunkNonce":  OCTET STRING [12 bytes]  — initial_nonce for per-chunk nonce derivation
  "chunkSize":   INTEGER                  — plaintext bytes per chunk (default 65536)
```

### Per-chunk nonce derivation

```
nonce_i[12] = initial_nonce[12] XOR (0x00000000 || uint64_be(i))

  bytes  0..3:  initial_nonce[0..3]  (unchanged — XOR with 0x00000000)
  bytes  4..11: initial_nonce[4..11] XOR uint64_be(i)
```

### Public API shape (directional)

```
set_random(random)                       // inject vscf_random; needed for start_encryption
set_key(data)                            // 32-byte AES-256 raw key
set_nonce(data)                          // 12-byte initial nonce (set before start_decryption)
set_chunk_size(size)                     // default: 65536

nonce() → vsc_data_t                     // read initial nonce after start_encryption (store in CMS)
nonce_len() → size                       // always 12

start_encryption() → status             // generates initial_nonce via random; validates key
encryption_out_len(data_len) → size     // upper bound including frame overhead
process_encryption(data, out) → status  // accumulate + flush full frames
finish_encryption(out) → status         // encrypt remaining bytes in pending

start_decryption() → status             // validates key and nonce are set
decryption_out_len(data_len) → size     // upper bound (GCM does not expand plaintext)
process_decryption(data, out) → status  // accumulate + decrypt full frames
finish_decryption(out) → status         // verify no partial frame pending
```

### Per-chunk encrypt/decrypt (internal, directional)

```
encrypt_chunk(plaintext, chunk_index, out):
    counter_bytes ← uint64_le(chunk_index)     // 8 bytes written to frame
    nonce_i       ← initial_nonce XOR (0x00000000 || uint64_be(chunk_index))
    aes256_gcm.set_nonce(nonce_i)
    aes256_gcm.set_key(self.key)
    aes256_gcm.set_auth_data(counter_bytes)    // counter authenticates chunk ordering
    ciphertext, tag ← aes256_gcm.auth_encrypt(plaintext, ...)
    out ← counter_bytes ‖ ciphertext ‖ tag

decrypt_chunk(frame, out):                      // frame = counter[8] + ciphertext + tag[16]
    counter_bytes ← frame[0..8]
    chunk_index   ← uint64_le(counter_bytes)
    ciphertext    ← frame[8..len-16]
    tag           ← frame[len-16..]
    nonce_i       ← initial_nonce XOR (0x00000000 || uint64_be(chunk_index))
    aes256_gcm.set_nonce(nonce_i)
    aes256_gcm.set_key(self.key)
    aes256_gcm.set_auth_data(counter_bytes)    // must match what encryptor used
    plaintext ← aes256_gcm.auth_decrypt(ciphertext, tag)
    // returns ERROR_AUTH_FAILED on tag mismatch
```

**Files:**
- Modify: `library/foundation/src/vscf_chunk_cipher.c`

**Approach:**
- Fill `@end` blocks for:
  - `init_ctx`: allocate `vscf_aes256_gcm`; allocate pending accumulation buffer
  - `cleanup_ctx`: release `vscf_aes256_gcm`; free and zero pending buffer (`vsc_buffer_delete`); zero key and nonce fields
  - `set_random`, `set_key` (copy 32 bytes), `set_nonce` (copy 12 bytes), `set_chunk_size`
  - `nonce` / `nonce_len`: read accessors for the `nonce[12]` property
  - `start_encryption`: validate key is set and random is injected; generate 12-byte `initial_nonce` via `random`; reset `chunk_index = 0`, reset pending
  - `start_decryption`: validate key is set and nonce is set (non-zero); reset `chunk_index = 0`, reset pending
  - `encryption_out_len` / `decryption_out_len`: return conservative upper bounds
  - `process_encryption`: append input to pending; while `pending_len >= chunk_size`, call `encrypt_chunk(pending[0..chunk_size], chunk_index++)`, drain from pending
  - `finish_encryption`: call `encrypt_chunk` on all remaining bytes in pending (the partial final chunk)
  - `process_decryption`: append input to pending; while `pending_len >= chunk_size + 24`, call `decrypt_chunk(pending[0..chunk_size+24], out)`, drain from pending
  - `finish_decryption`: if `pending_len > 0 && pending_len < 24 + 1`, return `ERROR_BAD_ENCRYPTED_DATA` (incomplete frame); if `pending_len >= 25`, decrypt the final partial frame (size = `pending_len - 24`); verify pending is now empty
  - `encrypt_chunk` (private): compute `counter_bytes = uint64_le(chunk_index)`; derive `nonce_i = initial_nonce XOR (0x00000000 || uint64_be(chunk_index))`; call `vscf_aes256_gcm_set_nonce(nonce_i)`, `vscf_aes256_gcm_set_key(key)`, `vscf_aes256_gcm_set_auth_data(counter_bytes)`; call `vscf_aes256_gcm_auth_encrypt`; write `counter_bytes ‖ ciphertext ‖ tag` to out

- `is_nonce_used` guard: always call `vscf_aes256_gcm_set_nonce` immediately before each `encrypt_chunk` call — this clears the flag that mbedTLS sets after each `finish_auth_encryption`

- Edge case: encrypt empty input (`process_encryption(empty)` + `finish_encryption`) → `finish_decryption` succeeds with 0 bytes output
- Error path: tamper with ciphertext bytes (flip one bit) → `ERROR_AUTH_FAILED`
- Error path: tamper with GCM tag bytes (flip one bit) → `ERROR_AUTH_FAILED`
- Error path: tamper with counter field bytes in a frame → `ERROR_AUTH_FAILED` (counter is GCM `auth_data`; modified counter produces tag mismatch)
- Error path: truncate stream mid-frame → `finish_decryption` returns `ERROR_BAD_ENCRYPTED_DATA`
- Error path: `start_encryption` without `set_key` → returns error
- Error path: `start_decryption` without `set_nonce` → returns error
- Error path: decrypt with wrong key → `ERROR_AUTH_FAILED`
- Error path: after `ERROR_AUTH_FAILED` from a tampered frame, subsequent `process_decryption` / `finish_decryption` also return error (state poisoned; requires new `start_decryption`)
- Integration: encrypt with `process_encryption` in 7-byte chunks, decrypt with `process_decryption` in 1000-byte chunks → correct plaintext (stream reassembly at different granularity)

**Verification:**
- `cd build && ctest -R chunk_cipher --output-on-failure` passes all test cases
- `cd build && ctest --output-on-failure` (full suite) shows no regressions in other tests

## System-Wide Impact

- **Interaction graph:** `vscf_chunk_cipher` depends on `vscf_aes256_gcm` (composition) and `vscf_random` (injected, used once per encryption). It does not register in `vscf_key_alg_factory`, does not participate in `vscf_alg_id`, and does not affect any existing cipher. No callbacks or observers.
- **Error propagation:** `vscf_status_ERROR_AUTH_FAILED` from `vscf_aes256_gcm_auth_decrypt` propagates through `decrypt_chunk` → `process_decryption`/`finish_decryption` → caller. After an auth failure the cipher state is poisoned; re-use requires a new `start_decryption` call.
- **State lifecycle risks:** The pending buffer holds plaintext (encrypt path) or ciphertext fragments (decrypt path) — must be zeroed in `cleanup_ctx`. Key and nonce fields in the struct contain key material — must be zeroed in `cleanup_ctx`. `chunk_index` must reset on each `start_encryption`/`start_decryption`.
- **CMS integration handshake:** After `start_encryption`, the caller reads `nonce()` and stores 12 bytes in `vscf_message_info` custom params (key `"chunkNonce"`, type data). Before `start_decryption`, the caller reads `"chunkNonce"` from custom params and calls `set_nonce()`, and reads `"chunkSize"` and calls `set_chunk_size()`. This handshake is the caller's responsibility and is not tested in Unit 5 (no CMS dependency in the unit tests).
- **API surface parity:** No language wrapper code references `vscf_chunk_cipher` yet — bindings deferred. `vscf_foundation_public.h` gains one new include; all existing includes are unchanged.
- **Integration coverage:** The streaming reassembly path is the most complex invariant. The integration test (7-byte encrypt granularity vs. 1000-byte decrypt granularity) exercises frame boundary straddling end-to-end.
- **Unchanged invariants:** `vscf_recipient_cipher`, `vscf_aes256_gcm`, and all existing foundation classes are unchanged. The new class is purely additive.

## Risks & Dependencies

| Risk | Mitigation |
|------|------------|
| `is_nonce_used` flag not cleared: calling `auth_encrypt` without `set_nonce` reset fails | Always call `vscf_aes256_gcm_set_nonce(nonce_i)` immediately before each `encrypt_chunk`; the derived `nonce_i` is computed fresh per chunk |
| Nonce collision: same `initial_nonce` reused across two encryptions with the same key | `initial_nonce` generated randomly by `start_encryption` via `random`; caller must generate a new `initial_nonce` for each encryption session |
| Partial frame at stream end not detected | `finish_decryption` explicitly checks pending length and returns `ERROR_BAD_ENCRYPTED_DATA` if a partial frame remains (fewer than `chunk_size + 24` bytes but more than 0) |
| Counter field tampering not detected | Counter bytes are passed as GCM `auth_data`; modified counter invalidates the GCM tag → `ERROR_AUTH_FAILED` |
| Key/nonce material in struct not zeroed on cleanup | `cleanup_ctx` zeros `key[32]` and `nonce[12]` fields explicitly, and calls `vsc_buffer_delete` for pending buffer |
| Codegen snapshot test count drift | After running codegen, mechanically update affected assertion counts per `docs/solutions/best-practices/codegen-test-stale-assertions-2026-05-12.md` |
